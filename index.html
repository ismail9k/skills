Implement-Issues Flow

How agents take one issue from the queue to a ready pull request: who does each step, how the effort level changes the work, where you approve plans, and which model does which job.

/implement-issues low | medium | high

The three settings

Effort

Low, medium or high. It sets how much review and checking each issue gets. Pass it when you start the run. Without it, the run uses the saved setting, and if there is none, it asks you.

Plan approval

When it's on, each issue stops after its spec and plan and waits on a draft plan PR. You comment or add the plan-approved label, and a later run builds it.

Models

One model for each of ten jobs, such as a cheap one for implementation and a strong one for review. Each is set as a tier (cheap, standard or strong) or an exact model name.

Plan approval and models are saved in docs/agents/delivery.md in your repository. The run asks only for what that file doesn't settle, and offers to save your answers after showing you the change. There is no separate setup step.

Approving plans

With plan approval on, an issue spans two or more runs. Nothing needs to stay open in between, because the plan PR on GitHub holds the issue’s state.

Stage by stage

  1. Build the queue Dispatcher
    • Lists the open issues, then looks at each one’s pull requests and branches.
    • Sorts each issue:
      • a plan PR labeled plan-approved is built;
      • a plan PR with unanswered comments gets its plan revised;
      • any other plan PR waits;
      • any other PR or branch is skipped;
      • an issue with neither gets planned.
  2. Settle the settings Dispatcher
    • Prints the effort, plan approval, and the model for every job. A model your agent doesn’t offer stops the run.
    • Asks for what isn’t saved and offers to save it. Then asks whether to run the issues one at a time or several in parallel.
  3. Plan Planner, one per issue
    • Superpowers’ brainstorming works from the issue and decides how big the work is. A project gets a spec, and a quick spec check if it has its own model. A small change goes straight to the plan.
    • writing-plans writes the plan. The planner commits the spec and plan, and stops.
    • With plan approval on, the dispatcher opens a draft plan PR, and the issue waits for you.
  4. Build Build lead, one per issue
    • Low: the build lead builds every task itself, tests first.
    • Medium and high: it runs Superpowers’ per-task loop (Figure 4).
    • At every effort, one whole-branch review ends the build, followed by one fix pass if the review finds anything.
  5. Verify Dispatcher
    • Reads the log and the diff, then runs tests, lint and typecheck. The output goes to log files, and only results and failures are read back.
  6. Open the draft PR Dispatcher
    • An approved plan PR becomes the built PR, on the same branch. Otherwise a new draft opens. At high effort, the full suite runs once more first.
  7. Review A new review agent
    • Checks the PR against the issue at every effort. Reviews the code too only at high, because below that the build’s own review already covered it.
  8. Answer and mark ready Build lead, then dispatcher
    • The build lead fixes each finding, runs the checks, pushes, and replies to every comment.
    • At medium and high, the dispatcher re-checks the pushed head. At low, CI is the evidence.
    • CI failures go back to the build lead, up to 1, 2 or 3 tries. Then the PR is marked ready, and merging is up to you.
  9. Report Dispatcher
    • One table: each issue’s state, the effort, the plan state, and the model each job ran on.

The per-task loop

This loop runs at medium and high effort only, once per plan task. The fix-round cap is 2 at medium and 5 at high, so the escalation seat is used only at high.

Likely hot spots

This is a reading of the skills. Nothing here has been measured from a real run yet.

Unset jobs still inherit

If the settings file leaves them out, the planner, build lead and review agent use the session model, and both whole-branch reviewers use the most capable model. Set those jobs to bring the cost down.

Code written twice

The plan can hold the code, and the build writes it again. A small change skips the spec, but it still gets a plan and a build.

Two identical reviews at high

At high, the build’s whole-branch review and the PR’s code review read the same diff with the same prompt. Below high, the PR’s code review is off.

Checks of a commit already checked

At high, Stages 5 and 6 both check commit A. At medium and high, the Stage 8 recheck repeats the run the build lead just did.

Checks on a plan revision

A revision changes only Markdown, yet it runs the full checks, and the push triggers CI.

The build lead’s context at review time

It answers the review still carrying the build’s skills and bookkeeping. This is on purpose: the agent that built the code should answer for it.
